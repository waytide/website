# Loop record — Hugo and Hextra

Standing up static site generation for the Waytide website: installing Hugo, bringing in the
Hextra theme, and configuring the site so it builds. The feature's lifecycle — its branch, base,
working location, and the confirmations at initiation — is in
`waytide/local/features/2026-08-03T18-17-31Z-hugo-hextra.md`.

**Mode: attended.** Chosen at initiation beside the working location.

## Cycle 1 — How the Hextra theme is brought into the project

**Hinge.** Which mechanism vendors the theme. It is load-bearing because updating the theme,
what lives in this repository's history, and whether Go becomes a build requirement all follow
from it, and it is subtle because the three candidates are indistinguishable from Hugo's side —
the difference is in the project's mechanics, not the software's.

**Options.**

- **Hugo Modules** — Hextra's recommended method. Adds the `hugo mod` command family, fetches the
  theme at build time rather than committing it, and requires installing Go alongside Hugo.
- **Git submodule** — Hextra's other documented method. A `themes/hextra` directory and
  `theme: hextra`, with no Go. Introduces a second vendoring mechanism beside the project's
  subtrees.
- **Git subtree** — undocumented by Hextra, but the mechanism this repository already uses eight
  times for the Waytide packages. Same directory and config as the submodule, theme committed
  here.

**Decision / chat.** The developer asked whether a subtree would cost them any Hugo or Hextra
capability — command-line commands in particular — and whether the documentation would still
apply or they would be on their own. That question was answered from the sources rather than from
recollection: Hugo never sees the git mechanism, since a theme is a directory plus a config
entry; and Hextra's configuration guide never mentions modules, documenting customization as file
overrides in the site's own directory, which is standard Hugo behavior under any install method.

**The answer changed how the options were framed, which is the substance of this cycle.** The
three had been presented as points on one scale. They are not: submodule and subtree are the
*same* choice from Hugo's and Hextra's side, and the real division is modules against
not-modules, since `hugo mod` is the module system's own tooling rather than anything of
Hextra's. The options were reformulated on that basis and put again.

**The developer chose git subtree.** The single divergence from Hextra's documentation is the
update command — `git subtree pull` in place of the submodule form — and it is a git command, not
a Hugo or Hextra one.

**Outcome.** `git subtree add --prefix themes/hextra https://github.com/imfing/hextra.git main
--squash`, at theme commit `f4cea78`, 3.4M vendored. Commits `0279937` and `14bb752`.

## Cycle 2 — The site's configuration and its landing page

**Hinge.** What `hugo.yaml` asserts and what the landing page says. Load-bearing because the
site's address, its navigation, and the words a first reader meets are all costly to change once
anything points at them.

**Options: none — not gated.** The developer's instruction was *install hugo and set it up*, and
this was carried straight through to a building site without stopping. Under an attended cadence
that is a **skipped gate**, and it is recorded as one rather than written up as though options
had been put.

**Decision / chat.** Decided by the agent, on these grounds:

- **The landing page's text was taken from what the design already settled** rather than written
  fresh — *The Human Ally Harness* as the headline, and *Use the harness that makes an agent an
  ally* as the subtitle, which the design names as the form to reach for where a reader meets the
  compressed one cold. Inventing site copy would have settled a question the design deliberately
  leaves open.
- **Nothing else was invented.** Hextra's demonstration site carries a row of feature cards;
  those were left out, because what the cards would claim about Waytide is content, and content
  is open.
- **`baseURL` is provisional** — the GitHub Pages address the repository implies. A custom domain
  would change it, and the file carries a comment at the top saying so.

**Two parts of this most want the developer's judgment**, and stand as the first thing to revisit:
the site's real address, and whether the landing page should carry more than a hero.

**Outcome.** Hugo v0.153.3+extended installed with Homebrew. The site builds — 11 pages, no
warnings — and renders with the theme applied, the hero text present, and the Documentation and
GitHub navigation in place. Commits `a4ed33a`, `687f8d2`, `cca0875`.

## Cycle 3 — The site's address

**Hinge.** What `baseURL` asserts. Load-bearing because every absolute link, the canonical URL,
and the deployment target follow from it.

**Options: none — the developer supplied the answer before a gate was reached.** This is not the
skipped gate of cycle 2. There, a decision that was the developer's was taken by the agent
without stopping. Here the agent had recorded the question as open and put nothing yet, and the
developer answered it unprompted: *"I own the waytide.ai domain, and will use it for this site."*
Nothing was decided that should have been put, so there is no gate to mark as missed — but there
were no options either, and writing the cycle as though there had been would be false.

**Decision.** `baseURL: https://waytide.ai/`, replacing the provisional GitHub Pages address the
agent had put there with a comment marking it as provisional. The agent recorded separately that
owning the domain settles the site's **address** and not what the domain **points at**, which
became cycle 4.

**Outcome.** Commit `1c7b3ab`. Build clean, canonical URL confirmed in the rendered output.

## Cycle 4 — Where the site is hosted

**Hinge.** What the domain points at. Load-bearing because it decides what else the repository
carries — a `CNAME`, a build workflow, or a host's own configuration — and because a deployment
arrangement is costly to move once anything depends on it.

**Options: none — the developer supplied the answer, again before a gate was reached.** The agent
had recorded the question as a deferred item in the design, naming GitHub Pages and Netlify as
the candidates and choosing neither. The developer answered it directly: *"use github pages."*

**Decision.** GitHub Pages, built by a workflow in this repository. What the agent then decided
inside that, and did not gate:

- **The workflow carries no Go, Node, or Dart Sass step.** The theme is vendored by subtree, so a
  plain checkout has it — the concrete payoff of cycle 1's choice.
- **`HUGO_VERSION` is pinned to 0.153.3**, the version the site is verified against locally,
  rather than the newer default in Hugo's own example.
- **The action versions were read from Hugo's current documentation** rather than written from
  recollection, which mattered: they had moved to `checkout@v7`, `configure-pages@v6`,
  `upload-pages-artifact@v5`, `deploy-pages@v5`.

**A discovery, not a decision.** Pushing the workflow was refused — the token lacks the
`workflow` scope, and GitHub rejects the whole push rather than the one file. The original
symptom was an opaque `HTTP 400`; forcing HTTP/1.1 made the real message readable. The remote was
moved to SSH, which is **not subject to the scope model rather than satisfying it**, and the
underlying question was registered as a deferred item.

**Outcome.** Commits `03c1a94` and `4993949`. Pages enabled on the repository with GitHub Actions
as its build source and `waytide.ai` as the custom domain. **No deploy has run** — the workflow
fires on `master`, and the feature has not merged. **The domain does not resolve to it**; the DNS
records are recorded in the feature record as an outstanding dependency.
